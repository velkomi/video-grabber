# Сохранение VideoGrabber в облако

Дата: 10 октября 2026. Это исследование и предложение архитектуры. Облака не подключены, OAuth-приложения и платные ресурсы не созданы. Проверка на реальных пользовательских облаках ещё не проводилась.

## Решение

Добавить три назначения: «На компьютер», «В облако», «На компьютер и в облако». Первая реализация — Google Диск и Яндекс Диск через Windows-приложение. Пользователь подключает свой диск и выбирает папку; готовые видео, MP3, документы и уроки передаются с его компьютера в его облако. VPS хранит только задание, выбранное назначение и статус. Токены облака и содержимое файлов на VPS не передаются.

Для готового файла это копирование. Для HLS, отдельных аудио/видеодорожек, MP3 и закрытых курсов сначала нужна существующая локальная обработка. У режима «В облако» поэтому может быть временный рабочий файл на компьютере. Обещать универсальное сохранение любого курса без единого локального байта было бы неправильно.

## Готовая основа

**rclone** — предпочтительный транспорт первой версии: официальный поддерживаемый проект, Google Drive, Yandex Disk, OneDrive, Dropbox, S3 и WebDAV. Его MIT-лицензия не требует покупки; при распространении сохраняются уведомления и лицензии зависимостей конкретного бинарника. Версию и контрольную сумму нужно закрепить в runtime-инвентаризации, а не скачивать произвольный latest при каждом запуске. [Исходники](https://github.com/rclone/rclone), [лицензия](https://rclone.org/licence/).

Использовать `copyto` для файла и `copy` для дерева курса, с уникальной папкой задания. `copy` не удаляет лишние файлы назначения; это безопаснее для данной функции, чем зеркальная синхронизация. Однако совпадающий путь может обновиться: обязательна отдельная политика конфликтов «сохранить оба» по умолчанию. Не применять автоматически `sync`, `move`, `purge` или очистку корзины. [Документация copy](https://rclone.org/commands/rclone_copy/).

Официальный [Docker-образ](https://hub.docker.com/r/rclone/rclone) пригоден для будущего личного NAS/локального исполнителя. Размещать такой обработчик медиа на нашем VPS противоречит выбранной схеме. [Официальный web GUI](https://github.com/rclone/rclone-web) полезен как пример, но в VideoGrabber лучше собственный короткий интерфейс; публичный доступ к rclone Remote Control не нужен.

Обсуждения на форуме rclone и Reddit показывают важность квот, повторов и проверки завершения. Это ориентиры для тестов, а не гарантия текущих ограничений провайдера. Например, [разбор неудачной загрузки в Drive](https://forum.rclone.org/t/using-copy-to-upload-to-google-drive-fails/39837). Числа из старых Reddit-постов не переносить в тарифы продукта. Hugging Face не даёт преимуществ для этой задачи: модель и AI-инфраструктура не требуются.

## Провайдеры

| Провайдер | Подход | Ограничения первой версии |
|---|---|---|
| Google Диск | Локальный rclone; при необходимости отдельный Drive API адаптер с resumable upload | Загрузка байтов, а не универсальное «забери ролик по URL». Для продолжения после перезапуска нужно отдельно проверять возможности транспорта и сохранять состояние |
| Яндекс Диск | Локальный rclone или официальный REST API | Проверить квоту, завершение асинхронной операции, размер/MD5; крупный файл может долго финализироваться |
| OneDrive/Dropbox | Следующий этап через тот же интерфейс транспорта | Отдельная авторизация, квоты и тесты каждого провайдера |
| S3/WebDAV/NAS | Опционально для опытных пользователей | Не принимать произвольный серверный адрес для скачивания через VPS; подключения выполняются на пользовательском устройстве |

Google документирует resumable-загрузку больших файлов и ограниченный scope `drive.file`: доступ к созданным приложением или явно выбранным пользователем файлам. Начать с видимой папки VideoGrabber, созданной приложением; выбор любой существующей папки требует отдельной корректной модели Picker/доступа. `drive.appfolder` — скрытая служебная область, она не подходит как обычная видимая папка с видео. [Загрузка Google](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [права Google](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [rclone Drive](https://rclone.org/drive/).

Яндекс предоставляет REST API файлов и OAuth. Документация rclone подтверждает поддержку MD5, квот и особенности финализации крупных файлов. [Яндекс REST](https://yandex.ru/dev/disk/rest/), [rclone Yandex](https://rclone.org/yandex/). Отдельные страницы Яндекса по загрузке внешнего URL и папке приложения во время исследования недоступны/дают ошибку ссылки. Поэтому импорт публичного URL непосредственно силами Яндекса — только кандидат следующего этапа, а не обещанная функция. До внедрения нужны доступная первичная спецификация и реальный тест. Такой импорт в любом случае не заменит обработку HLS, закрытого курса и авторизованных источников.

## Можно ли совсем без рабочего файла?

Для части готовых потоков существует `rclone rcat`: вход поступает через stdin. Но маленькие объёмы буферизуются в RAM; точный размер нужен некоторым backend; после обрыва весь поток нельзя повторить, если он нигде не сохранён. Отдельные multipart-части повторяются лишь при поддержке провайдера. Поэтому потоковый режим — дополнительная оптимизация после обычной надёжной загрузки, а не база сохранения курсов. [Документация rcat](https://rclone.org/commands/rclone_rcat/).

В браузере непосредственная передача возможна только при доступных байтах файла и разрешённом CORS источника/назначения. Нельзя считать просмотр ролика в плеере доказательством возможности прочитать его байты. Для неподдерживаемого источника сайт и Mini App отправляют задание в подключённое Windows-приложение; если компьютер недоступен, показывают «Ожидаем компьютер». Скрытого fallback со скачиванием на VPS не должно быть.

## Интерфейс

«Куда сохранить» → «Облако» → «Подключить Google Диск / Яндекс Диск» → выбор папки → «Сохранить». Подключение облака отдельно от входа в VideoGrabber: вход через Google не означает разрешение работать с Google Диском. Показать имя подключения, папку и доступное место, если провайдер сообщает его.

Курс сохранять деревом `Название курса / 01 Модуль / 01 Урок.mp4`, рядом материалы и выбранный TXT. Не принуждать к одному большому ZIP. Локальный manifest хранит стабильные идентификаторы материалов и результат каждого файла: после сбоя продолжаем незавершённые файлы без повторного расходования уже учтённого скачивания. При частичном успехе: «Сохранено 18 из 20», с повтором двух файлов.

Статусы: «Подготавливаем», «Сохраняем в облако», «Проверяем», «Сохранено», «Недостаточно места», «Подключите диск снова», «Ожидаем компьютер». Две независимые стадии прогресса вместо «100%» в конце скачивания, когда облачная передача ещё идёт. Ссылку «Открыть папку» давать на личную папку провайдера; не делать материалы публичными автоматически.

В боте: выбор «Видео в чат / На компьютер / В облако», кнопка настройки облака открывает Mini App; обработка идёт на привязанном устройстве. Уведомление результата содержит название, качество, длительность и кнопку папки. Выбор «в облако» сам по себе не означает отправку копии видео в Telegram.

## Архитектура и защита

В инфраструктуре выделить `ICloudDestination` (подключение, папка, квота, upload, verify, cancel), `RcloneCloudDestination` и локальный `CloudTransferStore`. Не менять рабочий downloader: очередь получает отдельную стадию после готовности файла. На сервере только provider/destination ID, device ID, состояние и счётчики; облачный секрет не входит в Job API.

Облачные refresh-токены хранить на устройстве с DPAPI. Обычная конфигурация rclone содержит доступ к диску и сама по себе не считается защищённым хранилищем: нужны шифрованная конфигурация, ограниченные ACL и передача секрета дочернему процессу без аргументов командной строки. Не печатать конфиг, headers, signed upload URL и cookies в телеметрию. Windows DPAPI не защищает от уже скомпрометированного процесса того же пользователя.

OAuth: системный браузер, одноразовый state, PKCE там, где поддержан выбранным провайдером, зарегистрированный точный callback, короткий loopback listener. Пользователь явно подтверждает доступ; пароль облака VideoGrabber не принимает. Проверить минимальные права, отзыв, истечение, смену домена и политику верификации провайдера. Не обещать отсутствие проверки Google для публичного OAuth-приложения.

Запуск rclone — через массив аргументов без shell. Пути нормализовать и ограничить выбранной папкой; не допускать `..`, произвольных backend/команд и overwrite без выбранного правила. Ограничить параллельные передачи/повторы, учитывать Retry-After и квоту. Существующие пользовательские файлы не удалять. Возможная очистка только созданного данным заданием временного файла — после подтверждённого сохранения и отдельного выбранного пользователем правила.

## Этапы внедрения и приёмка

1. Утвердить модель рабочей папки и подключений; зарегистрировать отдельные официальные OAuth-клиенты, без расширения прав существующего входа.
2. Закрепить официальный rclone и лицензии; реализовать сохранение одного готового файла в две облачные системы в Windows.
3. Добавить manifest, дерево курса, повтор частичных ошибок и кнопку открытия папки.
4. Подключить выбор назначения сайта/Mini App/бота через существующий device handoff.
5. Только после этого проверить потоковый режим и возможный импорт публичных URL Яндексом.

Приёмка: Unicode/длинные имена, два одинаковых названия, >5ГБ, нехватка места, отключение сети/приложения, отзыв токена, неправильный аккаунт, курс со смешанными материалами, 429/5xx, совпадение размера/хэша после финализации. Отдельно проверить отсутствие медиа и облачных токенов на VPS. Возобновление внутри одного большого файла после перезапуска нельзя объявлять до теста конкретного backend.

Место в облаке оплачивает пользователь по своему тарифу; не покупать ресурсы автоматически. Сохранение допускается только материалов, на которые у пользователя есть права; эта функция не добавляет обход DRM или ограничений доступа.
